# スクレイピング・PC稼働監視画面仕様

作成日・更新日: 2026-10-25（Asia/Tokyo）

本書は初期実装の設計仕様。CPU・メモリなどPC全体の状態を初期リリースに含める。
起動・計測開始の手順は [ホスト監視の設定](../deploy/monitor/README.md) を参照する。
現在の配置は `10_architecture.md` とルートの `compose.yaml` に従う。

## 1. 目的・監視対象

Web画面から次の事項を確認できるようにする。

- スクレイピングの制御APIとスケジューラが動いているか。
- 何を取得中で、予定に対してどれだけ進んでいるか。
- 取得したデータがDBへ反映されているか。
- PC全体のCPU・メモリ・ディスクに余裕があるか。
- 異常の発生時刻と、その前後のPC負荷・取得状況。

PC全体、Dockerコンテナ、アプリケーションの状態は別の監視対象として扱う。
制御APIの `/health` 応答だけでスケジューラやPC全体を正常と判定しない。

## 2. 画面構成

URLは `/scrape/status`、画面名は「スクレイピング・PC稼働状況」。ログイン必須。
Overviewとナビゲーションから遷移できるようにする。

| 表示順 | エリア | 表示内容 |
|---|---|---|
| 1 | 稼働サマリー | PC状態、制御API接続、スケジューラ生存、自動取得ON/OFF、DB同期結果、異常理由 |
| 2 | PCリソース | CPU・メモリ・ディスクのゲージ、現在値、使用率、取得時刻 |
| 3 | 負荷の推移 | CPU・メモリ・ディスク・ネットワークの時系列、取得失敗・同期失敗の発生時刻 |
| 4 | 実行中・本日の進捗 | 対象日・競馬場・レース・データ種別、開始時刻、経過時間、状態別件数、次回予定 |
| 5 | 実行履歴 | 日時、手動／定期、対象、結果、処理時間、保存件数、展開式のエラー詳細 |
| 6 | DB同期 | 最終成功日時、直近の試行結果・エラー、次回予定 |

監視対象PCの識別名と計測範囲（例: 「実行PC全体」「Linux VM全体」）を表示する。
PCリソースと取得履歴の時刻は同じ日本時間で表示する。
色だけに頼らず、状態名・数値・理由を併記する。

## 3. PCリソースの計測項目

| 項目 | 表示・定義 | 初期対応 |
|---|---|---|
| CPU | 全論理CPUの容量を100%とした全体使用率、論理CPU数、コア別使用率を詳細展開 | 必須 |
| メモリ | 総容量、利用可能容量、使用量、使用率。使用量は総容量−利用可能容量とし、回収可能なキャッシュを一律に逼迫扱いしない | 必須 |
| スワップ | 総容量、使用量、使用率。未設定時は「未設定」 | 必須 |
| ディスク容量 | ファイルシステムごとの総容量・使用量・空き容量・使用率。OS、取得データ、DB、監視履歴の保存先を識別 | 必須 |
| ディスクI/O | 物理ブロックデバイスの読み書きの合計転送量/秒 | 対応可能な項目を表示 |
| ネットワーク | 対象の外部通信インターフェース名と合計送受信量/秒 | 必須 |
| 稼働時間 | OSの起動日時・稼働時間、監視収集プロセスの最終通信時刻 | 必須 |
| CPU温度 | センサーが取得できる場合のみ温度とセンサー名を表示 | 任意 |

容量はGiB/MiB、転送量はMiB/sなど単位を明記する。
CPUと転送速度は前回計測との差分から算出し、初回計測・再起動・カウンタ巻き戻り時は値なしとする。
同じファイルシステム上に複数の保存先がある場合、容量を重複加算しない。
ネットワーク全体値ではDockerブリッジ・仮想インターフェースの重複計上を避ける。
取得不能な項目は「非対応」、取得失敗は「取得失敗」とし、0や正常に置き換えない。

CPU温度の警告値は機器依存のため一律の初期値を設けず、閾値設定と警告機能は拡張候補とする。
GPU、ファン回転数、SMART、電源・バッテリーの詳細監視は拡張候補とする。

## 4. スクレイピングの状態と進捗

### 4.1 生存と進行の区別

- 制御APIの疎通、スケジューラの生存確認、実処理の最終進捗時刻を個別に保持する。
- スケジューラは、取得中・取得間隔待ち・計画生成中も10秒ごとに生存確認を更新する。
- 生存確認が60秒以上途絶えた場合は「異常」。初回の記録が届くまでは「未計測」とする。
- 生存確認が最新でも、実行中の処理が進まない場合は別途「処理遅延」を表示する。
- 初期版の処理遅延は、最終進捗から定期取得10分・手動取得30分を暫定閾値とする。
- 計画の許容時間を超えた未完了件数と、再試行待ちを「注意」として表示する。
- 次回実行待ち、非開催日、全件完了、自動取得OFFは障害としない。

### 4.2 ジョブ・進捗

ジョブには予定、実行中、再試行待ち、成功、失敗、スキップ、中断の状態を設ける。
状態別件数は重複させず、再試行回数を別途保持する。
成功は必要な解析・保存まで完了した状態とし、HTTP応答だけで成功としない。
保存件数0は「保存対象データなし・未公開または対象なし」としてスキップ表示し、DB同期成功とは別に表示する。
公開状態の詳細な分類は取得元のパーサー判定を拡張する段階で対応する。

ジョブID、計画の版、予定・開始・終了時刻、最終進捗時刻、対象、試行回数、保存件数、失敗理由を永続化する。
再起動で未完了になった処理は「中断」とし、再実行との関係を追跡できるようにする。
計画再生成時は現在の計画の件数を集計し、古い計画の履歴を混在させない。
履歴は日付・競馬場・結果で絞り込み、ページングして表示する。

## 5. PCの警告判定

以下は運用開始時の暫定値で、設定から変更可能とする。
使用率の判定は10秒周期のサンプルを用い、所定時間連続して閾値以上の場合に成立する。
閾値未満が60秒続いたら解除する。欠測時は判定を保留し、監視データの状態を表示する。

| 項目 | 注意 | 異常 |
|---|---|---|
| CPU全体 | 80%以上が5分継続 | 95%以上が5分継続 |
| メモリ | 80%以上が5分継続 | 90%以上が5分継続 |
| ディスク容量 | 80%以上 | 90%以上 |
| 監視データ | 最終計測から30秒以上経過 | 最終計測から60秒以上経過で「監視不能」 |

ディスク使用率は計測時点の値で判定する。最低空き容量は初期版では全監視対象に共通の値を設定できる。
保存先ごとの異なる最低空き容量の設定は拡張候補とする。
スワップ使用だけでは異常判定せず、メモリ不足を調べる補助情報として表示する。
閾値超過はPC負荷の警告であり、スクレイピングの失敗と同一視しない。
監視データが途絶えてもPC停止とは断定せず、「監視不能・最終通信時刻」を表示する。
画面がAPIへ接続できない場合は、API接続失敗として表示する。

## 6. 更新・履歴

- PC計測は画面を閉じていても10秒周期で実行する。ブラウザの閲覧数で計測頻度を増やさない。
- 画面は10秒周期で最新状態を取得。非表示タブでは停止し、復帰時に更新する。
- 手動更新、自動更新ON/OFF、最終計測時刻、画面最終取得時刻を表示する。
- グラフ期間は直近1時間、24時間、7日。全グラフの時間軸をそろえる。
- 10秒サンプルを24時間、1分集計を7日保持する。集計値は平均・最大値・有効サンプル数を持つ。
- 欠測はグラフ上の空白として表示し、0埋めや欠測をまたぐ補間をしない。
- 履歴画面ではリソース警告、取得失敗、同期失敗を時系列で確認できるようにする。
- ジョブ履歴と解消済み警告イベントは30日保持する。新規ジョブ開始時／計測値受信時に期限を超えたデータを削除する。
- 情報更新に失敗した場合は前回値とその取得時刻を残し、「最新情報を取得できません」と表示する。

## 7. 収集・API構成

### 7.1 PC全体の収集

ホストOS上にPython標準ライブラリのみを使用する専用の監視収集プロセスを置き、OSのメトリクスを読み取る。
収集プロセスはスクレイピングと独立させ、scraper停止時もPC計測を継続する。
10秒ごとに既存Web入口経由の専用APIへ計測値を送信し、専用のサービス認証と送信権限を使用する。
ブラウザからホストOSを直接参照せず、通常のAPIを経由して表示する。
計測・送信に時間制限を設け、障害時も業務処理を待たせない。
送信失敗時は最大10分相当のサンプルを上限付きで保持し、復旧後に計測時刻を維持して再送する。
再送時はPC ID・OS起動IDと収集プロセス起動識別子・連番で重複を除外し、古い計測値で最新状態を上書きしない。

現在の構成を踏まえ、初期実装のホスト収集対象はLinux PCとする。
WSLやDocker Desktopなど仮想環境の場合は、計測対象がVMか物理PCかを明記する。
物理PC全体の表示には実ホストOS側の収集が必要で、VM内の値を物理PCの値として表示しない。
稼働先ごとに保存先のホストパスを設定する。

計測に必要な情報だけを読み取り、任意コマンド実行機能やDockerソケットの公開は追加しない。

### 7.2 API

パスはAPI内のパス。ブラウザからは既存の `/api/` 経由で利用する。

| API | 用途 |
|---|---|
| `GET /scrape/status` | 制御API・スケジューラ生存、実行中処理、計画進捗、同期結果 |
| `GET /scrape/jobs` | ページング・絞り込み付き履歴 |
| `GET /scrape/jobs/{job_id}` | 処理結果・エラー詳細 |
| `POST /system/metrics` | 専用収集プロセスからの計測値受信。送信権限必須 |
| `GET /system/metrics` | PC全体の最新計測値・警告・鮮度 |
| `GET /system/metrics/history` | 指定期間・粒度の時系列 |
| `GET /system/events` | PC警告の履歴。取得失敗は `/scrape/jobs`、直近の同期失敗は `/scrape/status` から表示 |

メトリクスはPC ID、起動ID、連番、計測範囲、計測時刻、受信時刻、各項目の値・単位・取得状態を持つ。
計測範囲は `host` / `vm` / `container` を明示する。
APIはブラウザとの時刻差に依存せず、サーバー側で鮮度と警告を算出する。
受信時刻より30秒を超える未来・15分を超える過去の計測値はAPIで拒否する。
各監視対象の失敗を個別に返し、PC計測失敗だけで取得進捗まで非表示にしない。
監視APIの認証・権限はサーバー側で検証し、画面のログイン制御だけに依存しない。
PCの履歴と時系列は既存PostgreSQL内の業務テーブルと分けた監視用テーブルに保存する。
scraperの生存状態とジョブ履歴は共有controlディレクトリ内のSQLiteに保存し、監視書き込みの失敗で取得処理を止めない。
グラフの取得失敗マーカーは、履歴の現在のフィルター・ページに表示中のジョブが対象。
同期失敗マーカーは直近の同期試行が対象で、全期間の同期履歴の保存は拡張候補とする。
描画粒度は1時間が10秒、24時間が2分、7日が10分。平均・最大値を切り替え、有効サンプルだけから集計する。

## 8. 初期リリースと拡張

初期リリースにはPC全体のCPU・メモリ・スワップ・ディスク容量・ネットワーク・稼働時間、
時系列グラフ、閾値警告、スケジューラ生存監視、ジョブ追跡、DB同期結果を含める。
ディスクI/OとCPU温度は計測可能な環境で表示する。

次段階ではサービスごとのCPU・メモリ・再起動回数・OOM終了の表示を追加する。
コンテナの値はPC全体と分け、CPUの分母やメモリ上限の有無を明示する。
PC全体が高負荷でも、個々のサービスが低負荷の場合を表現できるようにする。
任意起動のmlflow・pipelineが停止している場合は、起動対象外として扱う。
外部通知と画面からのサーバー再起動は拡張候補とする。

## 9. 受け入れ条件

1. PC全体のCPU・メモリ・保存先別ディスク使用状況が数値と推移で確認できる。
2. ホストOSの監視ツールと同じ定義・同じ時間帯で比較でき、コンテナやVMの値を混同しない。
3. 画面を閉じていても収集され、再表示時に履歴を確認できる。
4. CPU・メモリは継続時間付きで警告し、一時的な上昇で直ちに異常としない。
5. 最終計測から60秒で監視不能と判定し、次の画面更新で反映する。古い値を現在の正常値として表示しない。
6. 非対応センサー・未設定スワップ・欠測・再起動時のカウンタ初期化を正しく表示できる。
7. APIが応答していてもスケジューラ停止を検出し、待機・非開催日・自動取得OFFは障害扱いしない。
8. 手動取得の受付から成功／失敗／中断まで追跡でき、取得成功と同期失敗を区別できる。
9. 計測・履歴保存・監視APIの障害が、スクレイピングやDB同期を停止させない。
10. 認証なしでは監視情報を取得・送信できず、閲覧権限のみでは計測値を送信できない。
