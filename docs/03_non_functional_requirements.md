# Non-Functional Requirements（非機能要件）

更新日: 2026-01-04（Asia/Tokyo）

## 1. 目的
- 本プロジェクト（収集・保存・同期・可視化・学習）の運用に必要な **非機能要件（NFR）** を明文化し、設計・実装・テストの判断基準にする。
- NFR は「技術設定」ではなく **運用契約**（SLO/監査性/再現性）として扱う。

## 2. 適用範囲
- 対象: `api-service` / `scraper-service` / `frontend` / `reverse-proxy` / `postgres`
- 本ドキュメントは **原則**を定める。個別要件の正は `docs/test/00_test_requirements.md`（TR-xxx）とする。

## 3. 性能（Performance）
### 3.1 フロントエンド（frontend）
- **初期表示**: PC ローカル環境での初回表示が実用上ストレスにならないこと（目安: 数秒以内）。
- **一覧 UI**: テーブル/一覧の表示は必要に応じて表示件数を制限し、操作レスポンスを維持する（例: 先頭 N 件表示 + 注記）。
- **巨大コンテンツ**: `docs/test/data` のような Markdown（大きなテーブル）を表示する場合、UI が固まりにくい構造にする。
  - 例: 「一覧→クリックで詳細表示」/ 必要なファイルだけをロードする（全件一括ロードしない）。

### 3.2 API（api-service）
- **タイムアウト/リトライ**: ネットワーク断や 429/5xx を想定し、フロント側のタイムアウト/再試行方針を運用契約として整理する（実装も追従）。
- **ページング**: `GET /races` 等の一覧はページングを前提とし、過負荷を避ける（フロントは `page_size` を調整可能にする）。

## 4. 可用性・耐障害性（Availability）
- **劣化動作**: backend が落ちている/疎通不可でも、フロントは落ちずにエラー表示ができる（白画面にしない）。
- **オフライン参照**: ローカルに存在するドキュメント/テストデータは、API なしでも閲覧できる導線を確保する（デバッグ/検証用途）。

## 5. セキュリティ（Security）
- **入口統制**: 外部入口は `reverse-proxy` のみ（`docs/10_architecture.md`）。
- **トークン管理**: access token の保存方式は XSS リスクを考慮し、必要に応じて見直す（現状: localStorage）。
- **出所不明データの描画**: HTML 文字列をそのまま挿入しない。Markdown/JSON の表示は安全なレンダリング経路を使う。

## 6. 運用性・可観測性（Operability / Observability）
- **ユーザーに原因が分かるエラー**: 通信失敗/認証失敗/入力不正は UI 上で識別可能にする（ステータスやメッセージ）。
- **変更容易性**: ドキュメント更新 → テスト要件追加 → テスト追加 → 実装の順で追従できるよう、仕様の根拠をトレース可能にする。

## 7. アクセシビリティ・UX（Accessibility / UX）
- **キーボード操作**: 主要操作（フォーム送信、タブ切替、一覧選択）がキーボードで完結できること。
- **可読性**: 表や長文は折り返し/横スクロール等で破綻しないこと。

## 8. 保守性（Maintainability）
- **画面増殖の抑制**: いたずらに画面を増やさず、「一覧→詳細（展開/パネル/タブ）」で情報密度を上げる。
- **契約の正**: 画面仕様は `docs/11_frontend_screen_list.md` / `docs/12_frontend_screen_transitions.md` を正とする。
