# Project Concept（プロジェクトコンセプト）

## 1. 背景
本プロジェクトは「競馬のオッズ等を定期収集し、機械学習（分類）と強化学習により意思決定を最適化し、
ダッシュボードで可視化する」ことを目的とする。運用上は、スクレイピング負荷を抑えつつ、学習・評価・配布を自動化し、
変化（サイト構造/データ欠損/モデル劣化）に耐える仕組みを構築する。

## 2. 成功指標（暫定）
- 収集: 指定時刻（例：5分前/1分前/確定）でのオッズスナップショット取得率 ≥ 99%
- データ品質: 主要テーブルの欠損率/異常値率を閾値内に維持（詳細は `20_data_contracts.md`）
- 学習: 定期学習が失敗しても自動リトライし、失敗原因が追跡可能
- 可観測性: 収集/学習/推論のメトリクスがダッシュボードで追跡可能
- ビジネス: 回収率の向上（※保証しない。検証の再現性・監査性を最優先）

## 3. 非目標（スコープ外）
- 不正アクセスや規約違反に該当し得るスクレイピング（回避・制限を最優先）
- “常に勝つ”や“必ず回収率150%”の保証
- 初期フェーズでの大規模Kubernetes運用（将来移行は想定）

## 4. 制約・前提
- Raspberry Pi 5 がスクレイピング常駐ノード
- Ubuntu PC が DB/API/学習パイプライン/可視化の中心
- スクレイピングは対象サイトの規約・robots.txtを尊重し、負荷抑制を遵守（`30_scraping_policy.md`）
- すべて docker / docker compose を前提にし、環境差分を最小化

## 5. 設計原則
- TDD（テスト→仕様→実装）の順で進める。仕様変更は docs を先に更新する
- マイクロサービスは「責務境界の固定」が目的。初期は最小分割＋明確な契約で始める
- MLOps は「追跡可能性（データ/コード/実験/モデル）」を最優先する
